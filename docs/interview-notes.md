# 面试笔记（Phase 1）

每题先自己答一遍，再对照要点。答不出来的回代码里找依据。

## 1. 为什么反投影要用 `camera_info`，而不是自己假设焦距？

`camera_info` 的 `K` 矩阵给出 `fx, fy, cx, cy`，`D` 给出畸变系数。焦距随分辨率缩放变化，写死会在换分辨率后全错；真实相机还有径向/切向畸变，需要 `image_geometry` 校正后再反投影。仿真相机畸变为 0，但接口要按真实相机写。

## 2. 为什么红色需要两个 HSV 区间？

OpenCV 的 H 范围是 0–179，红色在色相环上跨 0° 边界，落在 `[0,10]` 和 `[170,179]` 两段，必须分别 `inRange` 再按位或。其他颜色单区间即可。

## 3. 为什么先开运算再闭运算？

开运算（先腐蚀后膨胀）去掉背景上的小噪点、反光斑；闭运算（先膨胀后腐蚀）填补目标内部的小孔。反过来的话，闭运算可能先把噪点和目标连成一片，后续开运算会削掉目标的细窄部分。

## 4. `cv_bridge` 用 `bgr8` 和 `rgb8` 有什么区别？

OpenCV 默认通道顺序是 BGR，`cv_bridge` 转到 `bgr8` 后 `cv::imshow` / `inRange` 的通道语义才正确。用错会红蓝互换，HSV 分割结果完全错误。Gazebo 输出 RGB，桥接转成 `sensor_msgs/Image` 后由 `cv_bridge` 负责转换。

## 5. 图像话题为什么用 SensorData QoS？

`sensor_data` = `best_effort` + `volatile` + depth 5。图像 30 Hz，允许丢帧但不能积压；reliable 在高负载下会重传旧帧，延迟越滚越大。

QoS 兼容性是单向的：reliable 发布端可以服务 best_effort 订阅端，反过来不行。若发布端是 best_effort、订阅端要求 reliable，现象就是「话题存在但收不到数据」。

## 6. `use_sim_time` 的作用？为什么桥接和感知节点都要开？

开启后节点用 `/clock`（Gazebo 仿真时间）而非系统时间。这样 TF、消息头时间戳、`rosbag` 记录、`tf2` 查询全部在同一时间轴上；仿真暂停时时间也暂停。本项目的 bridge 发布 `/clock`，所有参与节点都设 `use_sim_time:=true`。

## 7. `ros_gz_bridge` 参数里的方向符怎么读？

`话题@ROS消息类型[gz消息类型`：`[` 表示 Gazebo → ROS，`]` 表示 ROS → Gazebo。例如 `/camera/image@sensor_msgs/msg/Image[gz.msgs.Image` 是把 gz 图像导入 ROS。写反方向不会报错，只是没数据。

## 8. `camera_link` 和 `camera_optical_frame` 有什么区别？

`camera_link` 遵循 REP-103：x 前、y 左、z 上。相机光学坐标系遵循 REP-105：z 前（光轴）、x 右、y 下。针孔模型公式建立在光学坐标系上，所以 TF 树里要有 `camera_optical_frame`（或等价的固定旋转），否则位姿的轴会对不上。

## 9. 写出针孔模型反投影公式，深度图要注意什么？

已知像素 `(u,v)` 与深度 `Z`：

```
X = (u - cx) * Z / fx
Y = (v - cy) * Z / fy
Z = depth
```

然后用 TF2 把点从 `camera_optical_frame` 变换到 `base_link`。注意 Gazebo 深度图单位可能是毫米，需 `/1000` 转米；无效值（0 或 NaN）要过滤。

## 10. KDL 逆解为什么会失败？怎么提高成功率？

常见原因：目标超出工作空间、关节限位、奇异位形、种子解离目标太远导致迭代不收敛。处理：用当前关节角作 seed；失败时换几个 seed 重试；检查 KDL 返回的错误码；对不可达目标直接拒绝而不是下发无效轨迹。

## 11. 反投影时为什么取检测框顶面中心，而不是轮廓质心？

轮廓质心包进了方块可见的侧面，像素位置会被拉向侧面；直接反投影会把目标算低、算偏，误差可达厘米级。俯视相机下顶面中心更接近方块中心，所以用 bbox 的 `(0.5W, 0.3H)` 采样深度，再用内参反投影。这个比例可以按与真值的 XY 误差在线调。

## 12. 串口是字节流，为什么不能直接按固定长度读？

串口没有消息边界：一次 `read` 可能拿到半帧、两帧，或从一帧中间开始。所以协议要自带帧头 `AA55` 用于重同步、`len` 用于确定 payload 边界、CRC 用于拒收误码帧。解析器用状态机逐字节喂入，坏 CRC/超长帧只计数并回到找帧头状态，不阻塞后续帧。

## 13. ACK 为什么要回显 seq？

ACK 可能在超时重发之后才到，只回「成功」无法判断它对应哪一次请求。回显原 seq 后，桥只接受序号匹配的 ACK（`transact_mutex_` 保证同时只有一个事务在等）；超时 500 ms 重发 3 次，仍失败就向上返回错误，而不是无限等。

## 14. 为什么状态用话题、命令用服务？

状态是 10 Hz 的周期流，丢一帧无所谓，用 topic；关节目标需要确认 MCU 真的收到，用 service + ACK，失败能立刻反馈给调用方。两者都走同一条串口，靠 cmd 字节区分。
